# REST_AREAS.md — can mapd surface rest areas along the highway? (feasibility)

**Question (2026-06-23):** can the **pfeiferj mapd** component (the Go binary openpilot shells out to
for OSM speed limits + curve speeds) detect/expose **rest areas / service areas** along
interstates — and if not, what would it take to add it?

**Answer: No. mapd does not — and cannot from the tiles it currently ships — surface rest areas.**
The source data exists in OSM but is stripped before it ever reaches the car.

---

## Why mapd can't see them (three independent layers)

Verified against mapd v2.0.6 (pinned in `pnw/pnw-pilot/mapd_release.json`). mapd is purely a
**ways + speed-limit + curvature** engine; POIs are out of scope by design.

1. **Tile generation discards all POI nodes.** `~/gh/comma/mapd/maps/generate_offline.go`:
   - `scanner.SkipRelations = true` (relations skipped).
   - the scan switch keeps **only `*osm.Way`** objects; standalone OSM **nodes and their tags are
     thrown away** (`default: way = nil`).
   - from each way it reads only `name`, `ref`, `hazard`, `maxspeed[:forward/:backward/:advisory]`,
     `lanes`, `oneway` — it never reads `highway`, `amenity`, or any POI tag.
2. **The offline tile schema has no POI slot.** `~/gh/comma/mapd/cereal/offline/offline.capnp` has a
   `Way` struct (name/ref/maxSpeed/bbox/nodes/lanes/advisorySpeed/hazard/oneWay/…) and `Offline`
   (`List(Way)`). **There is no node / POI / amenity type at all.**
3. **The output schema has no rest-area field.** `MapdOut` in `pnw/pnw-pilot/cereal/custom.capnp`
   exposes wayName/wayRef/roadName/speedLimit/nextSpeedLimit/hazard/advisorySpeed/oneWay/lanes/
   suggestedSpeed/visionCurveSpeed/mapCurveSpeed/… A `grep restArea` across the whole tree returns
   **zero** matches. (The only `services` handling in `maps/way.go` is name-string *filtering to avoid
   attaching to* service roads — the opposite of detecting them.)

And the device pulls **pre-built tarballs** from `https://map-data.pfeifer.dev/offline/{lat}/{lon}.tar.gz`
(`mapd/settings/download.go`), generated by pfeiferj running `generate_offline.go` → uploaded to R2.
Since generation drops nodes, **the rest-area data is gone before it reaches the device** — a fork-side
*reader* can't recover it from the existing tiles either.

## The data exists in OSM (just not in mapd's tiles)

Rest areas are well-represented in OpenStreetMap:
- `highway=rest_area` — rest stop, no fuel (US Interstates are overwhelmingly this).
- `highway=services` — full service/travel plaza with fuel (mostly tolled roads).

Both are tagged on **nodes and areas (closed ways), not plain ways/relations** — large ones are areas,
small ones are center-point nodes. Refs: [highway=rest_area](https://wiki.openstreetmap.org/wiki/Tag:highway=rest_area),
[highway=services](https://wiki.openstreetmap.org/wiki/Tag:highway=services).

---

## What it would take to add it

### Option (a) — full mapd-side support (heavy)
1. `generate_offline.go`: stop discarding nodes — also handle `*osm.Node`, keep `highway=rest_area`/
   `highway=services` (and closed-way areas → centroid), storing lat/lon + name + a type/amenity flag.
2. Add a `RestArea`/`Poi` struct + list to `offline.capnp` (regenerate `offline.capnp.go`).
3. Runtime: compute nearest upcoming rest area along the predicted path + distance (analogous to
   `nextSpeedLimit` / `nextHazardDistance` in `way.go`/`upcoming.go`).
4. Add `restAreaAhead` / `restAreaDistance` (+ name/hasFuel) to `MapdOut` in `custom.capnp`, mirror
   into the fork's `cereal/custom.capnp`, add UI.
5. **Rebuild the mapd binary**, re-pin in `mapd_release.json`, and **regenerate + self-host the offline
   tiles** (or ship PNW-only tiles).
- **Blockers:** mapd is **upstream prebuilt** (PNW doesn't compile it — needs a fork + Go/earthly/capnp
  build), and the **hosted tiles have no POIs** (needs self-hosting). Effort: multi-day. Upstreaming to
  pfeiferj is plausible (he invites feature PRs) and would solve the binary/hosting problem if accepted.

### Option (b) — openpilot-side, bypass mapd for POIs (recommended for PNW) ✅
The I-5 PNW corridor is fixed and rest areas are static, so query OSM **independently of mapd**:
- Build a small offline lookup table of I-5 WA/OR rest-area coordinates **once** via Overpass
  (`highway=rest_area` in the corridor box), ship it with the fork.
- An on-device process checks GPS against it and publishes **distance-to-next-rest-area** on a custom
  cereal message → UI ("rest area in X mi").
- **No mapd fork, no tile regen, no hosting.** Effort: small-to-moderate. Tradeoff: a parallel data
  path (doesn't reuse mapd's way-matching/predicted-path), so accuracy at complex interchanges is
  cruder than (a) — fine for "next rest area ahead" on I-5.

**Bottom line:** rest areas are stripped at tile-build and absent from both the tile schema and
`MapdOut`. For the narrow PNW I-5 use case, the standalone OSM lookup (option b) is the far cheaper
route and sidesteps the prebuilt-binary / hosted-tile blockers entirely.
